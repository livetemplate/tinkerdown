# Plan: a CI onefile app, with live runs, the failing log and rerun

State — Done: plan signed off (user, 2026-11-22: add sort; issues #353–#355 opened), Phase 1 (`sort`, #356, v0.7.2), Phase 2 built; a merge idle fix it needs (v0.7.3). Next: the fix's release, then the onefile PR.

## Context

The next [onefile](https://github.com/livetemplate/onefile) app is `ci`: your GitHub Actions runs as a live list. A running run shows its jobs as they finish, and a failed run shows its failing job's log, with buttons to rerun failed jobs or cancel. It runs from its URL, and every command comes from your flags, like `containers`.

It was chosen as the most needed developer app that no editor already shows live:

- GitHub Actions is used by 62% of developers for personal projects and 41% of organizations, rising to 47% in 2026 ([JetBrains 2025](https://blog.jetbrains.com/teamcity/2025/10/the-state-of-cicd/), [2026](https://blog.jetbrains.com/teamcity/2026/10/state-of-cicd-2026-report/)).
- 69% of respondents say they waste time because of slow or unreliable CI/CD ([Harness 2026](https://www.harness.io/state-of-devops-modernization-2026), a vendor report).
- The tools developers star for it: act 73k, gh-dash 13k, and GitHub's CLI 47k (checked 2026-11-22). Git UIs rank higher (lazygit 84k), but editors already have git panels.

The audit (2026-11-22, gh 2.89.0, against `livetemplate/tinkerdown`) settled these facts:

- `gh run list --json … --jq '.[]'` prints one compact JSON object per line, newest first. The fields include `databaseId`, `status`, `conclusion`, `workflowName`, `displayTitle`, `headBranch`, `event`, `createdAt`, `updatedAt`, `url` and `attempt`.
- A running run has `conclusion: ""`.
- `gh run view ID --json jobs` gives each job's `status` and `conclusion`, and its steps with theirs.
- `gh run view ID --log-failed` prints the whole log of each failed job, not only the failing step (2,130 lines for one run). Each line is `job<TAB>step<TAB>timestamp message`. The step was `UNKNOWN STEP` on every line, and the first line starts with a byte-order mark.
- `gh run rerun ID --failed` reruns only the failed jobs. `gh run cancel ID` cancels.
- The REST limit is 5,000 requests an hour for an authenticated user.
- tinkerdown's `in` check compares a number as `fmt.Sprint` prints it (`stream.Match.Matches`), so a run ID decoded as a float64 prints as `4.5014332554e+10` and never matches `?run=45014332554`.

## Product

| User journey | What they see | Built on |
|---|---|---|
| Wait for a run | the run's row turns from ● running to ✓ passed or ✗ failed, live | `--source NAME=` polling `gh run list`, keyed by run ID |
| Watch a run's progress | click the run: its jobs, each with its state, updating while it runs | merge `params` with `in`, `--source jobs=` polling `gh run view --json jobs` |
| Read why it failed | the failing job's log, under its jobs | `--source log=` running `gh run view --log-failed` once the run completes |
| Rerun what failed | **Rerun failed** on a failed row | `--action rerun=` |
| Stop a run | **Cancel** on a running row; it asks first | `--action cancel=`, `data-confirm` |
| Find a run | Running, Failed and Passed tabs; search by title or branch | `fields.status`, `fields.conclusion` tabs, `f.fields.displayTitle` |
| Open it on GitHub | the run's number links to its page | the row's `url` |

```
┌ CI ──────────────────────────────────────────────────────────────────────┐
│ [All] [Running] [Failed] [Passed]                                        │
├─────────────────────────────────────────────┬────────────────────────────┤
│ [ title or branch  ]              30 runs   │ #534 · CI                  │
│ ● running  CI   feat/x   #536  [Cancel]     │ ✓ Client Build & Lint      │
│ ✗ failed   CI   main     #535  [Rerun]      │ ✗ Go Tests: Build          │
│ ✓ passed   CI   feat/y   #534               │ ✗ Docker Build             │
│                                             │ --- failed log ---         │
│                                             │ FAIL TestFoo (0.02s)       │
└─────────────────────────────────────────────┴────────────────────────────┘
```

On a phone the pane sits below the list, and each row puts the title and branch on their own line under the state, as `containers` does.

## Decisions

- The list polls `gh run list` every 15 seconds in a shell loop, and prints every run each time. Rows are keyed by `[source, fields.id]`, so a run's row updates in place.
  alternative: `gh run watch` or a webhook; or poll every 60 seconds while no run is active
  because: `gh run watch` follows one run and redraws a terminal, and a webhook needs a public URL. A slower idle poll would leave a rerun run looking failed for up to a minute after the click
- The `ci` merge has `buffer: 200`. A run that leaves the 30-run window is no longer refreshed, so it becomes the least recently updated key and is dropped first once the buffer is full. Repos share the buffer. Up to six repos, every run in a window fits (6 × 30 = 180), so a busy repo can't push out a quiet repo's current runs. The README says to raise `buffer` beyond that.
  alternative: keep every run until the page reloads
  because: a long session would show more runs than GitHub's own list, without bound
- A failed poll doesn't stop the loop. `gh`'s error message, joined into one line so a multi-line error isn't cut to its last line, reaches the page as a stderr row, keyed `[source, ""]` so each repo shows one, styled as an error. The next good poll prints `{"cleared":true}`, which `drop: fields.cleared=true` turns into removing that row.
  alternative: hide `gh`'s errors
  because: a list that silently stops updating looks current when it isn't
- The feed adds `id` (`databaseId` as a string) and `repo` (from `url`) to each run with `--jq`. Params and actions use `id`.
  alternative: change `stream.Match` to print whole floats without an exponent
  because: the string keeps tinkerdown unchanged. A tinkerdown fix would be general, so it's worth its own issue (G1)
- A keyed merge gets `sort: PATH` (or `-PATH` for descending). Rows are ordered by that field instead of first-seen order: numbers compare as numbers, other values as strings, and ties keep first-seen order. `ci` uses `sort: -fields.createdAt`, so the newest run is first and existing rows never move.
  alternative: print runs oldest first and reverse the list with CSS `column-reverse`
  because: screen readers and keyboard focus follow the DOM, so they would run oldest first (user, 2026-11-22: add sort)
- One `--source` per repo, each with its own `--repo owner/name`. Rows carry `source`, and actions get the repo from the row (`data-repo` → `$TD_repo`).
  alternative: one source listing several repos
  because: `gh run list` takes one repo; one source each keeps the command short
- The pane has two merges with `params: {run: {in: ci.fields.id}, repo: {in: ci.fields.repo}, attempt: {in: ci.fields.attempt}}`, and their commands pass `--attempt "$TD_attempt"`. A rerun reuses the run ID with the next attempt, so the open pane's `in` check closes and clicking the row opens the new attempt, instead of showing the old attempt's log:
  - `jobs` polls `gh run view --json jobs` every 10 seconds until the run completes, one row per job
  - `log` polls `gh run view --json status,conclusion` every 30 seconds until the run completes. Unless it passed, it then prints each `##[error]` line of `--log-failed` with the 30 lines before it, or the last 200 lines when there's none. It keeps the job name, so several failing jobs stay apart. It cuts the step column (`UNKNOWN STEP` in the audit). The first plan kept the last 500 lines. In the Phase 2 audit, those were mostly the last job's cleanup, and could cut off an earlier job's error.
  alternative: one merge printing both
  because: jobs are keyed rows that update; log lines are not
- A command that finishes printing ends with `exec tail -f /dev/null`, so tinkerdown doesn't restart it and print everything again. Nothing lingers: a `params` merge's inputs stop 30 seconds after the last page showing them leaves, or after the page moves to another run, and stopping kills the input's process group.
  alternative: a `restart` option on `--source` flags
  because: flags can't set source options today (G2); `tail -f /dev/null` works on Linux and macOS, unlike `sleep infinity`
- Buttons by state, through CSS on the row's class: Cancel while `status` isn't `completed` (including `waiting` and `pending`, which `gh run cancel` accepts), Rerun when `conclusion` is `failure`, `startup_failure`, `cancelled` or `timed_out`.
  alternative: none considered
  because: a per-row `{{if}}` would end row-by-row updates (found in containers Phase 4)
- Cancel asks first (`data-confirm`). Rerun doesn't, because rerunning failed jobs only repeats work.
  alternative: none considered
- Each action command checks its values with POSIX `case` patterns before calling `gh`, since actions run under `sh -c`. `$TD_run` must be digits only, and `$TD_repo` must be `owner/name` with no `.`-led segment. Otherwise it exits with an error, which the page shows.
  alternative: trust the row's values
  because: unlike `params`, an action has no `in` check, so a value can be any string within the `TD_` rules (which already refuse a leading `-`). Only the page's own origin can send actions, so this guards against a hand-made message, not other sites
- The e2e test puts a fake `gh` first on `PATH` and runs the README command through bash. The fake prints runs from fixture files that change over time, and records each rerun and cancel. No test calls GitHub.
  alternative: test against a real repo
  because: CI has no GitHub token to spare, and real runs aren't repeatable; one manual run against `livetemplate/tinkerdown` checks the real output before release
- The README's poll intervals keep one repo well inside 5,000 requests an hour. The list costs 240 an hour. A pane open on a running run adds about 480: its jobs every 10 seconds, and the log's wait for completion every 30. The first plan counted 360, missing the log's own status poll (found by `/simplify` in Phase 2). The README says how to lengthen the interval for many repos.
  alternative: none considered

## Constraints

- tinkerdown stays unchanged. If an assumption fails, the fix is a separate tinkerdown PR, planned here first.
- Nothing in tinkerdown knows about GitHub.
- A remote page never defines a command: it names sources and actions that flags supply.
- Every documented command quotes its values: `"$TD_run"`, `"$TD_repo"`.
- e2e tests use real Docker Chrome and are never skipped. They never call GitHub.

## Contract

The run feed's JSON line: `{"id", "repo", "databaseId", "number", "status", "conclusion", "workflowName", "displayTitle", "headBranch", "event", "createdAt", "updatedAt", "url", "attempt"}`.
- `status`: `queued`, `in_progress`, `completed`, `waiting`, `requested` or `pending`.
- `conclusion`: `""` while running; then `success`, `failure`, `startup_failure`, `cancelled`, `skipped`, `timed_out`, `action_required`, `neutral` or `stale` (the values `gh run list --status` takes).

The job row: `{"name", "status", "conclusion", "failed"}`, where `failed` names the failed steps.

`new?` in Files marks a path that doesn't exist yet.

```
params:   run: {in: ci.fields.id}   repo: {in: ci.fields.repo}   attempt: {in: ci.fields.attempt}
actions:  rerun   gh run rerun "$TD_run" --failed --repo "$TD_repo"
          cancel  gh run cancel "$TD_run" --repo "$TD_repo"
          each first runs: case "$TD_run" in ''|*[!0-9]*) exit 1;; esac
                           case "$TD_repo" in */*/*|.*|*/.*|*[!A-Za-z0-9_./-]*) exit 1;; ?*/?*) ;; *) exit 1;; esac
```

Defaults: list poll 15s, jobs poll 10s, `--limit 30` runs per poll, `buffer: 200` runs, the last 500 log lines.

## Results

- A1, through bash and `sh -c` against `livetemplate/tinkerdown`: the feed prints one JSON line per run with `id` as a string and `repo` derived, plus the `cleared` line. The `jobs` command prints a row per job with its failed steps, then `{"done":true}`, so the `jobview` merge has `drop: fields.done=true`. A failed `gh` call's multi-line usage text arrived joined into one line.
- A2, A4, A5, A6: `TestCI` and `TestKeyedSort_E2E` pass them. A3 was false (see the tracker).
- `--log-failed` prints nothing for a passing run, and the first fixture shows that an empty log must print nothing, not a blank line.
- A merge with `params` kept its rows for 5 minutes but its inputs stopped after 30 seconds, so reopening a run within those minutes showed its log twice, four times on the third visit. Fixed in tinkerdown #358 (a merge drops its rows when its shortest input does, and reseeds from its inputs when it restarts), to ship in v0.7.3. The containers app had the same bug.
- The manual run of the README command against `livetemplate/tinkerdown` widened the list to 150 runs to reach a failed one. It showed 150 runs newest first. The failed run showed its three jobs with their failed steps, and a 118-line log holding all 12 `##[error]` lines, starting with the real failure.
- On a long list, clicking a run far down scrolled the pane away, so on wide screens the runs scroll on their own.
