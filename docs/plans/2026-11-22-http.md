# Plan: an http onefile app, with saved requests and a Send button

State — Done: nothing. Next: plan sign-off, then Phase 1.

## Context

The next [onefile](https://github.com/livetemplate/onefile) app is `http`, the first entry in its [roadmap](https://github.com/livetemplate/onefile/blob/main/ROADMAP.md). It lists the requests in your [Hurl](https://hurl.dev) file, each with a Send button, and shows the response: status, time, headers, and the body, formatted when it's JSON. Editing the file updates the list.

It's first on the roadmap because HTTP clients are the most-starred job there (Hoppscotch 81k, Bruno 49k, Insomnia 40k, HTTPie 39k, Hurl 19k). The big clients ask for an account and workspaces before the first request, so many developers fall back to `curl` and raw JSON.

The audit (2026-11-22, hurl 7.1.0 via nix) settled these facts:

- `hurlfmt --out json FILE` prints the file's entries as one JSON object: `{"entries":[{"request":{"method","url","headers","body"},"response":{"status"}}]}`. It sends nothing.
- `hurl --from-entry N --to-entry N FILE` sends only entry N (1-based).
- With `--report-json DIR`, one run writes `DIR/report.json`. The report holds the status, `http_version`, response headers, timings in microseconds, each assert's result and a `curl_cmd`. The body is stored in a file under `DIR/store/`, named in `response.body`. So one Send sends one request.
- A secret set with `HURL_SECRET_<name>` or `--secret` shows as `***` in the report's headers and `curl_cmd`. A variable set with `HURL_VARIABLE_<name>` shows as written.
- A request that can't connect exits 3 and prints a multi-line error to stderr.
- tinkerdown can't do either of the two things this app needs (Phase 1):
  - It has no run that only a click starts. A `params` merge starts as soon as the URL holds its values, so reloading, Back or a shared link would send a POST again.
  - Keyed rows only leave through `drop`, so a request deleted from the file would stay listed.

## Product

| User journey | What they see | Built on |
|---|---|---|
| See my requests | one row per request: method, URL, line in the file | `--source requests=` printing `hurlfmt` output as a snapshot when the file changes |
| Edit a request | the list follows the file; a deleted request leaves | snapshot lines (Phase 1) |
| Send one | **Send** on the row; the pane shows ● sending, then the response | a merge with `on: send` (Phase 1), `--source send=` running hurl |
| Read the response | status, time, headers, and the body formatted when it's JSON, with links | the send command's summary line and body lines; `linkify` |
| See if it passed | each failed Hurl assert in red under the status | the report's `asserts` |
| Copy as curl | a **Copy curl** button, with secrets shown as `***` | the report's `curl_cmd` |
| Find a request | search by method or URL | `f.fields.url` |

## Decisions

- Requests live in the user's own `.hurl` file, read through `--source` flags. The page holds no requests.
  alternative: requests written into the page
  because: a page served from its URL can't read files, and the user's file stays theirs in git
- The file format is Hurl.
  alternative: `.http` (VS Code REST Client, JetBrains), or plain `curl` lines
  because: Hurl has a CLI that both parses a file without sending (`hurlfmt`) and sends one entry from it, with a JSON report. No common CLI does that for `.http`. The two formats are close for plain requests: method and URL, then headers, a blank line and the body, with `{{var}}` variables
- A link or URL never sends a request. Only a click on Send does.
  alternative: a `params` merge with `?entry=N`
  because: a URL is replayed by reloads, Back, Forward and shared links, which would send a POST or DELETE again
- tinkerdown gets a generic click-started run: `on: NAME` on a merge with `params` (Phase 1). A click on a button named NAME takes its `data-*` values as the params, checked by the same rules and `in` as URL values. It then clears the merge's rows and starts its inputs with `TD_<name>`.
  alternative: an `--action` whose output shows on the page
  because: `--action` has a 30-second timeout and keeps no output. A merge already streams, buffers and shows rows, and `tasks` (roadmap #4) needs the same run started by a click, including runs that take minutes
- A click-started input runs once: it isn't restarted when it exits, and has no timeout. A click while it runs kills its process group and starts again. The block's `.Running` is true while it runs.
  alternative: refuse a click while running
  because: a hung request would otherwise need a page reload to retry; `tasks` needs restart too
- Each connection shows the run of its own last click. Runs are shared by values, as `params` buffers are today, so two tabs sending the same entry see one run.
  alternative: one run per connection
  because: none considered beyond matching `params`
- tinkerdown gets snapshot lines (Phase 1). In a keyed merge, a JSON line that is an array replaces all of that input's rows, one row per element. A key missing from the new array leaves the list, and the page gets a remove for it. An array line may be up to 1 MiB, instead of the 16 KiB line cap.
  alternative: `drop` with a removed-marker row per deleted request
  because: the list command can't tell which request was deleted without keeping state. git and top (roadmap #3, #5) also print whole snapshots
- The `requests` command checks the file every second with `cksum`, and prints a snapshot only when it changed. Each element is `{entry, method, url}`, with `entry` as a string.
  alternative: `watchexec`, as the tests app uses
  because: a second tool to install; one `cksum` a second costs nothing. A string `entry` avoids the float printing in #353
- When `hurlfmt` fails on a half-edited file, its error shows as a stderr row and the last good list stays. The next good snapshot prints `{"cleared":true}` first, which `drop` removes, as `ci` does.
  alternative: none considered
- The `send` command runs hurl once into a fresh `mktemp -d` report directory, with `--max-time 30`. It prints one summary JSON line (`kind: summary`, status, time in ms, HTTP version, headers, failed asserts, `curl_cmd`), then the body: through `jq .` when it parses as JSON, otherwise as it is. It removes the directory. It stops the body at 4,000 lines and prints a line saying where it stopped.
  alternative: `hurl -i` for headers and body
  because: `-i` has no timings, asserts or `curl_cmd`. Running hurl twice would send the request twice. The 4,000-line limit keeps the summary inside the merge's 5,000-row buffer
- A body that isn't text (by its `content-type`) prints one line with its type and size instead.
  alternative: none considered
- Both commands check `$TD_entry` is digits only with POSIX `case` before running hurl, as `ci`'s actions do.
  alternative: rely on `in`
  because: a second check in the command costs one line, and the command is the user's to read
- The response pane uses one row markup for the summary and body lines. CSS hides the parts that don't apply, by `class="k-{{.fields.kind}}"`. It also resets tinkerdown's level colours inside the pane, since a body line holding "error" isn't a log level.
  alternative: `{{if}}` per row
  because: a per-row `{{if}}` ends row-by-row updates (containers Phase 4)
- The README tells users to set tokens with `HURL_SECRET_<name>`, so they show as `***` in the pane and in Copy curl. It says plainly that a response body that echoes a token shows it.
  alternative: none considered
- One `requests`/`send` pair per file. Several files need several pairs.
  alternative: a list across files
  because: `--from-entry` counts within one file; several files can come later if asked for

## Files

tinkerdown (Phase 1, worktree `.worktrees/click-run`):
- `internal/config/config.go`, `parser.go`: `On` on merge sources, mirrored. Validation: needs `params`; NAME isn't a builtin action, an approved action or another merge's `on`.
- `internal/server/websocket.go`: an action named by a merge's `on` checks its values like URL params, records them on the connection, and restarts that merge's inputs. It never reaches the action runner.
- `internal/stream/hub.go`, `proc.go`: run-once inputs with no restart and no timeout; restart on demand (kill the group, clear rows); `.Running`.
- `internal/stream/keyed.go`, `parse.go`: array lines as snapshots, with the 1 MiB cap for them.
- `internal/runtime/state.go`: `.Running` on the block's state.
- Tests: `internal/stream` (snapshot replace and removes; run once; restart kills the old group), `internal/config` (validation), e2e `TestClickRun_E2E` new? using only `sh` commands (no hurl, no network).
- Docs: `docs/sources/stream.md` (`on`, `.Running`, snapshot lines); `CHANGELOG.md` under `[Unreleased]`.

onefile (Phase 2, worktree `.worktrees/http`):
- `http/index.md` new?: merges `requests` (`inputs: ["*"]`, `key: [fields.entry]`) and `response` (`inputs: [send]`, `on: send`, `params: {entry: {in: requests.fields.entry}}`, `buffer: 5000`); search, the row Send buttons, the pane, Copy curl, the CSS for row kinds and the phone layout.
- `http/README.md` new?: install Hurl, the copyable serve command, secrets with `HURL_SECRET_`, what the pane shows, the 4,000-line limit. `http/docs/desktop.png`, `phone.png` new?.
- `e2e/http_test.go` new?: `TestHTTP`, running the README command with real hurl against an `httptest` server. `e2e/testdata/http/api.hurl` new?.
- `README.md`: a row for `http`. `ROADMAP.md`: mark `http` built, and say the requests live in your Hurl file.

## Acceptance criteria

- [ ] `/simplify` has run on each phase's diff.
- [ ] tinkerdown `go test ./internal/stream/... ./internal/config/...`: a snapshot replaces an input's rows and reports removed keys; a run-once input isn't restarted on exit; a restart kills the old group (no orphan `sleep` in `pgrep`); validation refuses `on` without `params` and `on` named like a builtin.
- [ ] tinkerdown `TestClickRun_E2E`, with console, server log, WebSocket frames and HTML captured:
  - a click starts the run and its rows appear; `.Running` is true, then false
  - a second click mid-run clears the rows and starts again; the first process is gone
  - opening the page with the values in its URL, reloading and Back start nothing
  - a hand-made action message with a value not in the `in` merge runs nothing and shows an error
  - a snapshot line that leaves out a key sends a remove op for its row
- [ ] The full tinkerdown suite passes, then a release through `release.sh` and a Homebrew formula bump, each signed off.
- [ ] onefile `cd e2e && go test -run TestHTTP ./...`, with real hurl against an `httptest` server and no internet:
  - the list shows the fixture's requests; adding a request to the file adds a row within 2 s, deleting one removes its row
  - Send on a POST shows its status, time, headers and formatted JSON; the server saw exactly one POST
  - reloading the page and pressing Back send nothing more (the server's count is unchanged)
  - a failing assert shows in red; a connection refused shows hurl's error; a half-edited file shows `hurlfmt`'s error and keeps the list
  - Copy curl holds `***`, never the `HURL_SECRET_` value
  - a body holding `<script>` renders as text; a body over 4,000 lines shows the cut line
  - a hand-made action with `entry=1;x` runs nothing
  - on a phone no cell leaves its row; no browser console errors
- [ ] The full onefile suite passes: `cd e2e && go test ./...`.
- [ ] Served from its raw GitHub URL, the page loads with the README command copied as published.
- [ ] `prereview check` passes on the changed docs.

## Constraints

- Nothing in tinkerdown knows about HTTP or Hurl. Phase 1's tests use only `sh`.
- A remote page never defines a command: it names sources that flags supply.
- No URL, reload or link sends a request.
- Every documented command quotes its values: `"$TD_entry"`.
- e2e tests use real Docker Chrome and are never skipped. They never use the internet.

## Contract

```yaml
requests: {type: merge, inputs: ["*"], key: [fields.entry]}
response: {type: merge, inputs: [send], on: send, buffer: 5000,
           params: {entry: {in: requests.fields.entry}}}
```

The snapshot element: `{"entry": "1", "method": "GET", "url": "https://…/users"}`.

The summary line: `{"kind": "summary", "status", "ms", "http_version", "headers": [{"name", "value"}], "failed_asserts": [{"line", "message"}], "curl"}`. Body lines are plain text, with no `kind`.

The Send button: `<button name="send" data-entry="{{.fields.entry}}">`.

Defaults: file check every 1 s, `--max-time 30`, 4,000 body lines, a 5,000-row response buffer, a 1 MiB cap for snapshot lines.
