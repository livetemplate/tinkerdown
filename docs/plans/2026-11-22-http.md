# Plan: an http onefile app, with saved requests and a Send button

State — Done: nothing. Next: plan sign-off, then Phase 1.

## Context

The next [onefile](https://github.com/livetemplate/onefile) app is `http`, the first entry in its [roadmap](https://github.com/livetemplate/onefile/blob/main/ROADMAP.md). It lists the requests in your `.http` file, each with a Send button, and shows the response: status line, headers, time, and the body, indented when it's JSON. Editing the file updates the list.

It's first on the roadmap because HTTP clients are the most-starred job there (Hoppscotch 81k, Bruno 49k, Insomnia 40k, HTTPie 39k). The big clients ask for an account and workspaces before the first request, so many developers fall back to `curl` and raw JSON.

`.http` is the format developers already keep requests in. The VS Code REST Client reads it (7.8M installs), every JetBrains IDE has it built in, and httpyac and rest.nvim read it too. Hurl's format (19k stars) is read by Hurl alone (VS Code Marketplace and GitHub, checked 2026-11-22).

Three rules from review (user, 2026-11-23) shape the design:
- The app is one file, `http/index.md`. The user downloads nothing else.
- It uses only tools already on macOS and most Linux systems, so curl sends.
- tinkerdown never sends HTTP itself. It reads the `.http` file and starts curl.

The audit (2026-11-22, curl 8.18.0) settled these facts:

- `curl -w '%{json}'` prints one JSON line with `http_code`, `method`, `http_version`, `content_type`, `size_download`, `time_total` in seconds, `url_effective`, `exitcode` and `errormsg`. It needs curl 7.70 (2020).
- `curl -i` prints the status line and response headers before the body. `-H @-` reads headers from stdin, one per line (curl 7.55).
- In `sh`, `${TD_body:+--data-binary "$TD_body"}` gives curl two arguments when there's a body, newlines kept, and none when it's empty. So a GET sends no body.
- tinkerdown can't do three things this app needs (Phase 1):
  - It can't read a `.http` file.
  - It has no run that only a click starts. A `params` merge starts as soon as the URL holds its values, so reloading, Back or a shared link would send a POST again.
  - A command gets only the button's values, each at most 256 bytes on one line, so it can't get a request's headers and body.

## Product

## What the code looks like

This section is a sketch: the audits can change the details. The app is the serve command and the page; tinkerdown's three features follow.

### The serve command (in `http/README.md`)

```sh
tinkerdown serve --allow-exec https://raw.githubusercontent.com/livetemplate/onefile/main/http/index.md \
  --source 'api=http:./api.http' \
  --source 'send=printf "%s" "$TD_headers" | curl -sS -i --max-time 30 -X "$TD_method" -H @- ${TD_body:+--data-binary "$TD_body"} -w "\n%{json}\n" -- "$TD_url"'
```

`api.http` is the user's file. tinkerdown sets the `TD_` values from the clicked request, with its variables filled in.

### The page (`http/index.md`)

```yaml
---
title: HTTP
sources:
  requests:
    type: merge
    inputs: ["*"]
    key: [fields.entry]
    accepts: {kinds: [http], min: 1, hint: "--source api=http:./your.http; see the README"}
  response:
    type: merge
    inputs: [send]
    on: send
    buffer: 5000
    line_max: 1MiB
    params:
      entry: {in: requests.fields.entry}
---
```

~~~markdown
```lvt
<main lvt-source="requests">
  <form name="Filter" role="search">
    <input type="search" name="f.fields.text" placeholder="name, method or URL" aria-label="Search requests"
           lvt-on:input="Filter" lvt-mod:debounce="250">
  </form>
  <small>{{len .Data}} requests</small>
  {{if .Error}}<p><mark>{{.Error}}</mark></p>{{end}}
  <ol class="reqs">
    {{range .Data}}
      <li data-key="{{.key}}">
        <b class="name">{{.fields.name}}</b> <code class="method">{{.fields.method}}</code>
        <span class="url">{{.fields.url}}</span>
        <button name="send" data-entry="{{.fields.entry}}" aria-label="Send {{.fields.name}}">Send</button>
        <details><summary>request</summary><pre>{{.fields.headers}}

{{.fields.body}}</pre></details>
      </li>
    {{end}}
  </ol>
</main>
```

```lvt
<aside class="resp" lvt-source="response" aria-label="Response">
  {{if .Running}}<p aria-busy="true">Sending…</p>{{end}}
  {{if .Error}}<p><mark>{{.Error}}</mark></p>{{end}}
  {{if not .Data}}<p class="hint">Press Send on a request.</p>{{end}}
  <ol class="body">
    {{range .Data}}
      <li data-key="{{.seq}}" class="c{{.fields.http_code}} s-{{.stream}}">
        <b class="time">{{.fields.time_total}} s</b>
        <pre class="line">{{linkify (jsonindent .line)}}</pre>

```
~~~

The page's CSS (not shown) does three jobs:
- The summary row, the one with a `fields.http_code`, moves to the top with `order: -1` and shows only its time. Every other row shows only its line.
- It resets tinkerdown's level colours inside the pane, since a body line holding "error" isn't a log level.
- It lays the response pane beside the list on wide screens, as `containers` does.

The `{{if}}`s sit outside the ranges, so every row in a range uses the same markup.

### tinkerdown (Phase 1)

- **The `.http` reader:** `--source NAME=http:PATH` reads the file whole, and again whenever it changes. Each read replaces the input's rows. Each request becomes a row with these `fields`:

  | Field | Value |
  |---|---|
  | `entry` | its position as a string, `"1"` first |
  | `name` | from `###` or `# @name` |
  | `method` | `GET` for a bare URL |
  | `url` | as written |
  | `headers` | one per line |
  | `body` | as written |
  | `text` | name, method and URL, for search |

  Fields keep `{{name}}` as written. The values with variables filled in go in the row's `Env`, which never enters template state.
- **Click-started runs:** `SourceConfig.On string` (`yaml:"on"`), next to `Params`. The WebSocket action handler checks a map of `on` names before the action runner. On a match, it checks the button's values with the merge's params rules and finds the row they name. It then calls `hub.Restart` with `TD_<param>` plus that row's `Env` as `TD_method`, `TD_url`, `TD_headers` and `TD_body`. `Restart` kills the old process group, empties the buffer, and starts the inputs once.
- **Display and line length:** a `jsonindent` template function, and `line_max` on merges.

## Decisions

- Requests live in the user's own `.http` file, passed as a flag. The page holds no requests.
  alternative: requests written into the page
  because: a page served from its URL can't read files, and the user's file stays theirs in git
- The file format is `.http`.
  alternative: Hurl, Bruno's `.bru`, Postman collections, a file of curl commands
  because: it's the text format most developers already have, and the same file keeps working in their editor
- curl sends, from a `--source` flag. tinkerdown reads the file and starts curl, and never opens a connection itself.
  alternative: tinkerdown sends through its `rest` client; a downloaded `http.sh` that parses with awk and runs curl
  because: sending HTTP is not tinkerdown's job (user, 2026-11-23), and a second file breaks the one-file rule (user, 2026-11-23)
- tinkerdown gets a `.http` reader, `--source NAME=http:PATH`, a new flag kind beside `file:PATH`. It re-reads the whole file when its size or modification time changes, checked every 250 ms like the file tailer. Each read replaces the input's rows, so a deleted request leaves the list and the page gets a remove for it.
  alternative: a command printing JSON snapshots, and a generic "array line replaces rows" rule
  because: without a script, no command already on the machine can parse `.http`
- The `.http` subset: `###` separates requests, and text after it names the request. `# @name x` also names it. `#` and `//` start comments. The request line is `METHOD URL`, or a bare URL for GET, with an optional `HTTP/1.1` that's ignored. Headers run to the first blank line, and the body runs to the next `###`. `@name = value` lines define variables.
  alternative: none considered
- `{{name}}` takes the file's `@name` value, or else the environment variable `name`. tinkerdown fills variables into the row's `Env` only, so a token never reaches template state or the browser. A request with an unset variable gets no `Env`, and Send shows "unset variable name" without starting curl.
  alternative: fill variables into the shown fields; JetBrains' `http-client.env.json` environments
  because: a shown token can end up in a screenshot or a shared screen. Environment files are JSON with named environments, a feature of their own (G1)
- A file that doesn't parse shows the error with its line number in `.Error`, and the last good rows stay.
  alternative: none considered
- A link or URL never sends a request. Only a click on Send does.
  alternative: a `params` merge with `?entry=N`
  because: a URL is replayed by reloads, Back, Forward and shared links, which would send a POST or DELETE again
- tinkerdown gets a generic click-started run: `on: NAME` on a merge with `params`. A click on a button named NAME takes its `data-*` values as the params, checked by the same rules and `in` as URL values. It then clears the merge's rows and starts its inputs.
  alternative: an `--action` whose output shows on the page
  because: `--action` has a 30-second timeout and keeps no output. A merge already streams, buffers and shows rows, and `tasks` (roadmap #4) needs the same run started by a click, including runs that take minutes
- A click-started run also gets the `Env` of the row its params name in the `in` merge, as `TD_` values. These values can be multi-line and up to 128 KiB, unlike button values, because they come from the server's own rows, not from the browser. 128 KiB is Linux's limit for one environment string (`MAX_ARG_STRLEN`). A longer value, or one holding a NUL byte, refuses the run with a message naming the field (G3).
  alternative: pass headers and body as button `data-*` values
  because: those come from the browser, so they keep the 256-byte, one-line limit, and a hand-made message could set any header
- A click-started input runs once: it isn't restarted when it exits, and has no timeout. A click while it runs kills its process group and starts again. The block's `.Running` is true while it runs.
  alternative: refuse a click while running
  because: a hung request would otherwise need a page reload to retry; `tasks` needs restart too. curl's `--max-time 30` ends a request that hangs
- Each connection shows the run of its own last click. Runs are shared by values, as `params` buffers are today, so two tabs sending the same request see one run.
  alternative: one run per connection
- The response is `curl -i`'s output, then `-w "\n%{json}\n"`'s summary line. The leading `\n` keeps the summary off a body's last line when the body has no trailing newline.
  alternative: `%{header_json}`; a temporary file for the body
  because: `-i` shows headers as curl prints them, in one run. A body file needs `mktemp` and cleanup in the flag
- A merge gets `line_max`, defaulting to 16 KiB. `response` sets 1 MiB, so a minified JSON body arrives as one line.
  alternative: raise the cap for every stream
  because: the cap protects log streams from one huge line; only this merge expects one
- tinkerdown gets a `jsonindent` template function: it indents a string that parses as a JSON object or array and returns any other string unchanged.
  alternative: `jq` in the flag
  because: jq isn't on most Linux systems by default
- The page uses one row markup for the summary and body lines. CSS hides the parts that don't apply, using a class from `fields.http_code`.
  alternative: `{{if}}` per row
  because: a per-row `{{if}}` ends row-by-row updates (containers Phase 4)
- One `api`/`send` pair per file. Several files need several pairs.
  alternative: a list across files
  because: an entry number counts within one file; several files can come later if asked for

## Files

## Constraints

- tinkerdown never sends HTTP for this app; curl does.
- The app is one file, `http/index.md`, plus the user's own `.http` file. The user downloads nothing else.
- The serve command needs only `sh` and `curl`.
- A remote page never defines a command: it names sources that flags supply.
- No URL, reload or link sends a request.
- e2e tests use real Docker Chrome and are never skipped. They never use the internet.

## Contract

The row from the `.http` reader: `fields` `{entry, name, method, url, headers, body, text}`, all strings; `Env` `{method, url, headers, body}` with variables filled in.

The click: `<button name="send" data-entry="{{.fields.entry}}">`. The command gets `TD_entry`, `TD_method`, `TD_url`, `TD_headers`, `TD_body`.

Defaults: re-read check every 250 ms, `--max-time 30`, a 5,000-row response buffer, `line_max` 16 KiB unless set, 1 MiB for `response`, 128 KiB for an `Env` value.
