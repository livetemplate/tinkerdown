# Plan: an http onefile app, with saved requests and a Send button

State — Done: nothing. Next: plan sign-off, then Phase 1.

## Context

The next [onefile](https://github.com/livetemplate/onefile) app is `http`, the first entry in its [roadmap](https://github.com/livetemplate/onefile/blob/main/ROADMAP.md). It lists the requests in your `.http` file, each with a Send button, and shows the response: status, time, headers, and the body, formatted when it's JSON. Editing the file updates the list.

It's first on the roadmap because HTTP clients are the most-starred job there (Hoppscotch 81k, Bruno 49k, Insomnia 40k, HTTPie 39k). The big clients ask for an account and workspaces before the first request, so many developers fall back to `curl` and raw JSON.

`.http` is the format developers already keep requests in. The VS Code REST Client reads it (7.8M installs), every JetBrains IDE has it built in, and httpyac and rest.nvim read it too. Hurl's format (19k stars) is read by Hurl alone (VS Code Marketplace and GitHub, checked 2026-11-22).

The app needs only tools found on macOS and most Linux systems: `sh`, `awk` and `curl` (user, 2026-11-22).

The audit (2026-11-22, curl 8.18.0) settled these facts:

- `curl -w '%{json}'` prints one JSON line with `http_code`, `method`, `http_version`, `content_type`, `size_download`, `time_total` in seconds, `url_effective`, `exitcode` and `errormsg`. It needs curl 7.70 (2020). `%{header_json}` prints the response headers as JSON and needs curl 7.83 (2022).
- `curl -K -` reads its options from stdin as a config file (`url = "…"`, `request = "POST"`, `header = "…"`). A value written there never passes through a shell.
- One run with `-o FILE -w '%{json}'` gives the body and everything the pane shows, so one Send sends one request.
- tinkerdown can't do either of the two things this app needs (Phase 1):
  - It has no run that only a click starts. A `params` merge starts as soon as the URL holds its values, so reloading, Back or a shared link would send a POST again.
  - Keyed rows only leave through `drop`, so a request deleted from the file would stay listed.

## Product

| User journey | What they see | Built on |
|---|---|---|
| See my requests | one row per request: its `###` name, method, URL | `--source requests=` printing `http.awk`'s list as a snapshot when the file changes |
| Edit a request | the list follows the file; a deleted request leaves | snapshot lines (Phase 1) |
| Send one | **Send** on the row; the pane shows ● sending, then the response | a merge with `on: send` (Phase 1), `--source send=` running curl |
| Read the response | status, time, headers, and the body formatted when it's JSON, with links | curl's `%{json}` line, then the body through `http.awk`'s formatter; `linkify` |
| Copy as curl | a **Copy curl** button, with variables left as `$name` | `http.awk`'s copy line |
| Find a request | search by name, method or URL | `f.fields.url` |

```
┌ HTTP · api.http ───────────────────────────────────────────────────────┐
│ [ search           ]   12 requests  │ Create user · 201 · 84 ms        │
│ List users   GET  /users     [Send] │ [Copy curl]                      │
│ Create user  POST /users     [Send]◀│ ▸ headers (7)                    │
│ Get user     GET  /users/{{id}}     │ {                                │
│                              [Send] │   "id": 42,                      │
│                                     │   "url": "https://…/users/42"    │
└─────────────────────────────────────┴──────────────────────────────────┘
```

On a phone the pane sits below the list, and each row puts the URL on its own line under the name:

## Decisions

- Requests live in the user's own `.http` file, read through `--source` flags. The page holds no requests.
  alternative: requests written into the page
  because: a page served from its URL can't read files, and the user's file stays theirs in git
- The file format is `.http`.
  alternative: Hurl, Bruno's `.bru`, Postman collections
  because: it's the text format most developers already have, and the same file keeps working in their editor
- curl sends the request, and a POSIX awk script, `http/http.awk` in onefile, reads the file. The README has the user download it and read it before use. It's about 150 lines and has three modes:
  - `list` prints the snapshot
  - `request N` prints curl's config for request N
  - `pretty` indents JSON
  alternative: tinkerdown reads `.http` itself; httpyac (needs Node); JetBrains `ijhttp` (needs Java or Docker); `jq` for formatting
  because: `sh`, `awk` and `curl` are on macOS and most Linux systems, and jq isn't on most Linux systems by default. Keeping the parser outside tinkerdown keeps the onefile rule that every command comes from the user's flags
- `http.awk` uses POSIX awk only, so it runs under macOS's awk, mawk and busybox as well as gawk.
  alternative: none considered
- The `.http` subset: `###` separates requests, and text after it names the request. `# @name x` also names it. `#` and `//` start comments. The request line is `METHOD URL`, or a bare URL for GET, with an optional `HTTP/1.1` that's ignored. Headers run to the first blank line, and the body runs to the next `###`. `@name = value` lines define variables.
  alternative: none considered
- `{{name}}` takes the file's `@name` value, or else the environment variable `name`. An unset variable stops the send with an error naming it, and nothing is sent.
  alternative: JetBrains' `http-client.env.json` environments
  because: reading JSON in POSIX awk is a project of its own (G1). Environment variables keep tokens out of the file
- A link or URL never sends a request. Only a click on Send does.
  alternative: a `params` merge with `?entry=N`
  because: a URL is replayed by reloads, Back, Forward and shared links, which would send a POST or DELETE again
- tinkerdown gets a generic click-started run: `on: NAME` on a merge with `params` (Phase 1). A click on a button named NAME takes its `data-*` values as the params, checked by the same rules and `in` as URL values. It then clears the merge's rows and starts its inputs with `TD_<name>`.
  alternative: an `--action` whose output shows on the page
  because: `--action` has a 30-second timeout and keeps no output. A merge already streams, buffers and shows rows, and `tasks` (roadmap #4) needs the same run started by a click, including runs that take minutes
- A click-started input runs once: it isn't restarted when it exits, and has no timeout. A click while it runs kills its process group and starts again. The block's `.Running` is true while it runs.
  alternative: refuse a click while running
  because: a hung request would otherwise need a page reload to retry; `tasks` needs restart too
- Each connection shows the run of its own last click. Runs are shared by values, as `params` buffers are today, so two tabs sending the same request see one run.
  alternative: one run per connection
- tinkerdown gets snapshot lines (Phase 1). In a keyed merge, a JSON line that is an array replaces all of that input's rows, one row per element. A key missing from the new array leaves the list, and the page gets a remove for it. An array line may be up to 1 MiB, instead of the 16 KiB line cap.
  alternative: `drop` with a removed-marker row per deleted request
  because: the list command can't tell which request was deleted without keeping state. git and top (roadmap #3, #5) also print whole snapshots
- The `requests` command checks the file every second with `cksum`, and prints a snapshot only when it changed. Each element is `{entry, name, method, url}`, with `entry` as a string.
  alternative: `watchexec`, as the tests app uses
  because: it's not installed by default. A string `entry` avoids the float printing in #353
- A file `http.awk` can't read shows its error as a stderr row, and the last good list stays. The next good snapshot prints `{"cleared":true}` first, which `drop` removes, as `ci` does.
  alternative: none considered
- The `send` command checks `$TD_entry` is digits only, pipes `http.awk request "$TD_entry"` into `curl -sS -K - --max-time 30 -o "$tmp" -w '%{json}'`, and joins `%{header_json}` onto that line. It then prints the body:
  - through `http.awk pretty` when `content_type` is JSON
  - as it is for other text, wrapped with `fold -w 4000` so no line passes the 16 KiB cap
  - as one line with its type and size when it isn't text

  It stops the body at 4,000 lines, prints a line saying where it stopped, and removes `$tmp`.
  alternative: `curl -i`
  because: `-i` has no timings. Running curl twice would send the request twice. The 4,000-line limit keeps the summary inside the merge's 5,000-row buffer
- Copy curl prints the request with `{{name}}` written as `"$name"`, never its value, so a copied command holds no token.
  alternative: the resolved command
  because: the copy goes to the clipboard and into chat; the user's shell fills the variable in when it runs
- The response pane uses one row markup for the summary and body lines. CSS hides the parts that don't apply, using a class from `fields.http_code`. It also resets tinkerdown's level colours inside the pane, since a body line holding "error" isn't a log level.
  alternative: `{{if}}` per row
  because: a per-row `{{if}}` ends row-by-row updates (containers Phase 4)
- One `requests`/`send` pair per file. Several files need several pairs.
  alternative: a list across files
  because: an entry number counts within one file; several files can come later if asked for

## Files

tinkerdown (Phase 1, worktree `.worktrees/click-run`):
- `internal/config/config.go`, `parser.go`: `On` on merge sources, mirrored. Validation: needs `params`; NAME isn't a builtin action, an approved action or another merge's `on`.
- `internal/server/websocket.go`: an action named by a merge's `on` checks its values like URL params, records them on the connection, and restarts that merge's inputs. It never reaches the action runner.
- `internal/stream/hub.go`, `proc.go`: run-once inputs with no restart and no timeout; restart on demand (kill the group, clear rows); `.Running`.
- `internal/stream/keyed.go`, `parse.go`: array lines as snapshots, with the 1 MiB cap for them.
- `internal/runtime/state.go`: `.Running` on the block's state.
- Tests: `internal/stream` (snapshot replace and removes; run once; restart kills the old group), `internal/config` (validation), e2e `TestClickRun_E2E` new? using only `sh` commands (no network).
- Docs: `docs/sources/stream.md` (`on`, `.Running`, snapshot lines); `CHANGELOG.md` under `[Unreleased]`.

onefile (Phase 2, worktree `.worktrees/http`):
- `http/http.awk` new?: `list`, `request N`, `pretty` and the copy line, POSIX awk only. Values in curl's config are quoted, with `\` and `"` escaped and newlines written as `\n`.
- `http/index.md` new?: merges `requests` (`inputs: ["*"]`, `key: [fields.entry]`) and `response` (`inputs: [send]`, `on: send`, `params: {entry: {in: requests.fields.entry}}`, `buffer: 5000`); search, the row Send buttons, the pane, Copy curl, the CSS for row kinds and the phone layout.
- `http/README.md` new?: downloading `http.awk`, the copyable serve command, tokens from environment variables, the `.http` subset, the 4,000-line limit, and the curl 7.83 minimum. `http/docs/desktop.png`, `phone.png` new?.
- `e2e/http_test.go` new?: `TestHTTP`, running the README command against an `httptest` server. `e2e/http_awk_test.go` new?: `http.awk` under every awk on the test machine (gawk, mawk, busybox). `e2e/testdata/http/api.http` new?.
- `README.md`: a row for `http`. `ROADMAP.md`: mark `http` built, and say the requests live in your `.http` file.

## Acceptance criteria

- [ ] `/simplify` has run on each phase's diff.
- [ ] tinkerdown `go test ./internal/stream/... ./internal/config/...`: a snapshot replaces an input's rows and reports removed keys; a run-once input isn't restarted on exit; a restart kills the old group (no orphan `sleep` in `pgrep`); validation refuses `on` without `params` and `on` named like a builtin.
- [ ] tinkerdown `TestClickRun_E2E`, with console, server log, WebSocket frames and HTML captured:

  - a second click mid-run clears the rows and starts again; the first process is gone
  - opening the page with the values in its URL, reloading and Back start nothing
  - a hand-made action message with a value not in the `in` merge runs nothing and shows an error
  - a snapshot line that leaves out a key sends a remove op for its row
- [ ] The full tinkerdown suite passes, then a release through `release.sh` and a Homebrew formula bump, each signed off.
- [ ] onefile `cd e2e && go test -run 'TestHTTP|TestHTTPAwk' ./...`, against an `httptest` server with no internet:
  - `http.awk` gives the same output under gawk, mawk and busybox awk for the fixture file, including a header holding `"` and `\` and a multi-line JSON body
  - the list shows the fixture's requests by name; adding a request to the file adds a row within 2 s, deleting one removes its row
  - Send on a POST shows its status, time, headers and indented JSON; the server saw exactly one POST, with the body and headers as written
  - reloading the page and pressing Back send nothing more (the server's count is unchanged)
  - `{{token}}` comes from the environment; an unset variable sends nothing and names it; Copy curl holds `"$token"`, never its value
  - a connection refused shows curl's error; a file that doesn't parse shows the error and keeps the list
  - a body holding `<script>` renders as text; a body over 4,000 lines shows the cut line; a one-line 100 KiB body arrives whole across folded lines
  - a hand-made action with `entry=1;x` runs nothing
  - on a phone no cell leaves its row; no browser console errors

- [ ] Served from its raw GitHub URL, the page loads with the README command copied as published.
- [ ] `prereview check` passes on the changed docs.

## Constraints

- Nothing in tinkerdown knows about HTTP or `.http` files. Phase 1's tests use only `sh`.
- The app needs only `sh`, `awk` and `curl`; nothing to install beyond tinkerdown.
- A remote page never defines a command: it names sources that flags supply.
- No URL, reload or link sends a request.
- Every documented command quotes its values: `"$TD_entry"`.
- e2e tests use real Docker Chrome and are never skipped. They never use the internet.

## Contract

```yaml
requests: {type: merge, inputs: ["*"], key: [fields.entry]}
response: {type: merge, inputs: [send], on: send, buffer: 5000,
           params: {entry: {in: requests.fields.entry}}}
```

The snapshot element: `{"entry": "1", "name": "List users", "method": "GET", "url": "https://…/users"}`.

The summary line is curl's `%{json}` object with `"headers"` (from `%{header_json}`) and `"curl"` (the copy line) added. Body lines are plain text.

The Send button: `<button name="send" data-entry="{{.fields.entry}}">`.

Defaults: file check every 1 s, `--max-time 30`, 4,000 body lines, `fold -w 4000`, a 5,000-row response buffer, a 1 MiB cap for snapshot lines.
